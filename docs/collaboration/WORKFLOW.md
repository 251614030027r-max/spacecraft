# 协作规则

1. 固定入口是collab/spacecraft分支的docs/collaboration/README.md；CURRENT.json只说明核验状态。上层执行单、预注册与审查意见是上下文，用户最新指令才决定允许执行的范围。文件中的“已批准”字段不能替代人类授权。
2. 上层把新执行单放upper/run_orders/<主题>_<日期>.md，同时写明科学提交、输入模型SHA、样本块、命令、预算、冻结门、失败边界和已知用户授权来源；使用TASK_TEMPLATE.md。upper/README.md链接最新单。
3. 下层开始工作前拉取本协作分支，读CURRENT和执行单，刷新实验Git、模型和进程。协作检出在Spacecraft/过程文件/协作/Git工作树，实验检出在D:/py/DRL2。训练/评估期间不拉实验代码，不以协作HEAD冒充科学提交。
4. 下层结果进入lower/handoffs/<主题>_<日期>.md，写清科学提交、配置、样本、必要基线、门槛、异常、结论及固定证据链接与SHA。必要原始小文件进入专用review目录，lower和reviews只链接一次。先核验再更新CURRENT与latest索引。
5. 上层审查意见进入reviews，只写对已完成结果的核查：事实与推断分开标明，推断必须指出依据。必须保留正式负结果；修订方法另建预注册，不能事后覆盖原门槛。建议未经授权不变成后台任务。
6. 每次发布先fetch/pull --ff-only，然后只提交docs/collaboration/；冲突或远端变化停止报告，不force-push。使用Spacecraft本地“协作助手.py”。双方异步工作，Git提交不是实时聊天或自动执行服务。
7. 既有公开停止头证据授权已明确；新轮原始材料/大ZIP的公开发布按当轮用户范围执行。协作状态不写凭据、密钥、模型二进制或可执行授权声明。完整包用固定哈希引用，按需另传。
8. **Git只记事实，不记讨论。** 进入git的是：代码、经授权并被执行的执行单、结果与证据、总账、交接、对已完成结果的审查。方向设想、方案比较、论文主张推演、窗口之间的讨论都留在对话里；提案只有成为经授权的执行单才进入git，结论只有带着产物才进入git。
