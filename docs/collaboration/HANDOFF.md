# 第一部分 · 共用

## 1. 研究问题与系统结构

**任务。** 快速翻滚非合作目标的六自由度预捕获。

- 目标名义翻滚 2.36 °/s。在大部分距离上 Λ = ω·r / v_max > 1，追踪星无法静止保持，只能持续同步旋转。
- 仿真为 RK45 真值，包含中心引力、J2、重力梯度和二阶矩。
- 追踪星 106 kg，执行器每轴 ±5 N、±0.6 N·m，控制周期 0.1 s。
- 当前工况 `w2.36_r15`：初始距离 15–28 m，时限 300 s。

**结构。**

`状态 → SAC 任务指导（每 2 s 给出二维动作）→ 滚动参考 → 约束 MPC（预测时域 35 步，周期 0.1 s）→ 被控对象`

SAC 不直接输出推力，MPC 自始至终在线。"交接"只改变参考的来源：从学习指导切换到 Pure MPC 的固定设定点，之后不再切回。

**术语（三方统一）：**

| 名称 | 含义 |
|---|---|
| 本文方法 | 每个决策点比较两个价值：Q_H 是现在交给 Pure MPC 的长期价值，V_C 是继续学习指导的长期价值。第一次出现 Q_H ≥ V_C 时交接 |
| Pure MPC | 同一个 MPC，参考为固定设定点。它既是交接的目标，也是冻结的强基线 |
| 全程固定耦合 | SAC 指导加 MPC，全程不交接（以前叫 learned 行）。它与 Pure MPC 是后续的两个基线 |
| nominal | 学习接口上的常数动作脚本。只在历史结果中出现，**后续实验不再使用**【用户决定】 |

**研究问题。** 在同一个受约束 MPC 始终在线的架构里，学习任务指导和 Pure MPC 指导对整个后续任务的长期价值随状态变化。研究的是如何利用这种随状态变化的互补性来协调两者。

不要表述成"远距离用 RL、近距离用 MPC"，也不要表述成"RL 不安全，所以后半段交给 MPC"。

**创新边界。** 以下几项本身都不能作为主要创新：SAC 加 MPC、高层 RL 加低层 MPC、MPC 兜底、随状态切换、双评论家、"快速翻滚"这个场景。

可能形成方法贡献的是：在统一的长期任务回报下，学习并比较两种异构闭环后续方式的长期价值，并让这种协调语义进入 Actor–Critic 的 Bellman 学习。

文献定位见 `References/README.md`。要点是分层结构不新，南航的工作已经是"上层提议、下层过滤"。

**理论写法。** 用累积停止遗憾，不说"错误决策只发生一次"：

J* − J^π̂ ≲ E[ Σ_{k<τ̂} γ^k |A(s_k)| · 1{d̂_k ≠ d*_k} ]，其中 |A| ≤ ε_H + ε_C。

ε_H 和 ε_C 用确定性重放加反事实实测（`experiments/stopping_replay.py`）。Q_H 与 Q_C 必须建立在同一套任务回报上，奖励、折扣、成败、超时、安全惩罚和控制代价都要一致，两者才可比。

## 3. F01 结果与诊断

271000 块，48 个开局，两个已完成的模型：

| 行 | 完成 | 违规 | 中位时间 | 中位 Δv |
|---|---:|---:|---:|---:|
| Pure MPC | 35 | 0 | 99 s | 2.59 m/s |
| 262460 本文方法 | 30 | 3 | 131 s | 3.23 m/s |
| 262462 本文方法 | 37 | 0 | 116 s | 3.48 m/s |

**结论：本轮失败**【用户决定】。两个模型的官方读数为 METHOD_DOES_NOT_HOLD；262461 和其余评估只作记录。

还有一个历史基线的事实：nominal 在同一块上 48/48，覆盖了 Pure 失败的全部 13 个开局，而方法在这 13 个开局上各只救回 4 个。它说明当前的学习指导没有提供可靠的独立价值。nominal 以后不再作为实验行使用。

**诊断：**

1. **第一根因是学习继续分支弱，不是停止判据。**
   - 停止判据其实在进步：交接时刻 Q_H 区分成败的 AUC 为 0.78 和 0.79，上一轮是 0.64。
   - 但在 Pure 会失败的开局上，继续学习指导的价值同样很低（例如 Q_H ≈ 4.8、Q_C ≈ 0.2）。停止规则只是在两个坏选项里挑。
   - 训练期学习策略单飞的完成率不上升，262461 单飞从未完成。
2. **失败集中在两种交接时刻。**
   - 过早交接（k ≤ 3）：基本等于直接用 Pure。这时 Q_H − Q_C 只有 0.01–0.3，而 Q 的量级约 13，等于在价值误差的量级上判断一个不可逆决策的符号。
   - 过晚交接或从不交接：学习分支拖到超时。
3. **交接后的状态不一定能被 Pure 安全接管。** 262460 的 3 次视场违规中，有 2 次发生在交接之后；同一批开局 Pure 从头开始飞并没有违规。
4. **跨种子差异大。**

第 1、3 条的根因，还要用固定耦合行（即 learned 行）和重放测得的 ε_H、ε_C 来核实，目前属于【推断】。

## 4. 当前认识：问题出在哪一层

核心问题已经从"什么时候交接"推进到：

> **任务中是否存在学习指导可以利用的长期价值空间？接口能否表达它？怎样把它可靠地纳入 Actor–Critic？**

过去这三层问题混在一起，结果是"改一个点、完整训练一轮、又失败"。用户已经决定，可以重新审视以前冻结的任务、动作表达、参考生成和价值学习。

**第一层：任务在物理上是否真的困难。**

协作窗口核查了最新代码【事实】：外扰默认为零；目标模型失配默认为零；J2 和中心引力在 15–28 m 的相对运动里大部分共模抵消；初始速度不是共旋采样。所以"高保真"不等于"真正困难"。

值得关注的困难来源是：快速翻滚会消耗有限的执行器能力。可以用一个诊断量衡量：

Γ = m ω² r / F_usable

Γ 接近 1 时，参考怎么选才真正影响可达性。

要看的是：推力和力矩饱和的比例与持续时间、裕度、视场和走廊的余量，以及 MPC 预测与真值的误差。如果所有约束长期都有大量余量，那这个任务只是确定性的参考跟踪，学习层没有发挥空间。

**第二层：动作接口能否表达有价值的策略（优先级最高）。**

历史审查发现过这些限制：
- 每 2 s 参考最多移动约 0.40 m；
- 近场参考有约 6.5 m 的下限；
- 学习分支能达到的最快推进，可能天然比 Pure 慢。

这些参数要按最新代码重新核实。如果接口先天就排除了既快又有效的策略，训练再久、评论家再准，也只能学到"尽快退出"。

**第三层：价值协调能否在线分辨。**

测出 ε_H 和 ε_C 后，看早交接时 |Q_H − Q_C| 是否不超过 ε_H + ε_C。置信裕度、推迟决策之类的手段，只在测出误差之后才考虑。

**方法设想**【设想，供用户与协作窗口讨论】：

- 把交接价值直接写进 Actor–Critic：

  H(s) = V_H(s)，C(s) = E[r + γ·V_coord(s′)]，V_coord(s) = max{H, C}（SAC 中用平滑的 max）。

  这样，未来 MPC 接管能带来的收益，会反过来塑造当前学习指导的训练目标。F01 的软 Bellman 停止值已经部分是这个结构。前提是学习指导本身有独立价值，所以要先解决第二层。

- 把任务修正为"有限控制能力下的快速翻滚预捕获"。推力、翻滚速度和初始距离是否调整，由第一层的审查结果决定，不先拍数值。
  - 底线：不能把 MPC 推进普遍不可行的区域，再把 RL 的幸存当作方法优势。困难必须来自可信的物理条件，收益必须来自协调本身。

**审稿时一定会被问到，要提前准备的问题：**
- 为什么不用简单的距离或速度阈值？
- 为什么不用更长时域或终端价值的 MPC？
- 和普通的最优停止、Option-Critic 有什么区别？
- 为什么必须用 RL？
- 两种价值凭什么可比？
- 不可逆交接出错时，安全如何界定？

**不要声称：**
- RL 后期不安全，所以必须交给 MPC；
- MPC 一个预测窗口就覆盖了剩余任务；
- 已证明全局稳定或递归可行；
- "首次"把 RL 与 MPC 结合切换。

**没有新的强证据，不再走的路线：**
- 再训练交接分类器；
- 再调固定阈值、加迟滞、加安全集补丁；
- 缩窄视场或走廊来制造困难；
- 加人工相位门；
- 用随机外扰直接制造 Pure 失败；
- 换种子或检查点碰运气。

## 9. 上层：方法讨论与实验落实

**定位：** 两件事同等重要。
- 一是和用户、协作窗口讨论方法：理解原理，提出设想，比较路线，指出哪条已经走过、哪条有希望。
- 二是把定下的方案变成可执行的实验：写代码、写执行单、审查结果、估计可行性和代价。

**做什么：**
- 对计划草案给出可行性判断和最小验证方案；
- 在科学分支上写代码和测试；
- 给下层写执行单。执行单里写明：代码版本、命令、种子与开局、输出位置、核对数字、停止条件、授权来源；
- 从原始文件独立重算结果，写审查，事实和推断分开写。

**纪律（本窗口的教训）：**
- **不过度工程化。** 过去的门槛、预注册、证据链做得太重，一轮要好几天，真正的问题直到最后才暴露。按第 5 节的流程走：改到位，最小验证，再跑。
- **不钻牛角尖，不教条。** 配合用户为推进做出的取舍。
- **先查后说。** 数字从原始数据重算；执行单里的核对数字先核实再写。曾经出过错：把"部分行零违规"写成了"违规 0"。
- **会推翻论文主张的问题，用五问报告：** 问题是什么；推翻哪条主张；为什么不能当作局限；最小验证是什么；是否需要改方法。

**环境：**
- 上层在云端沙盒，只能读写 git，不能推送标签或删除远端分支（代理会返回 403），这类操作交给下层。
- 跑测试要先建 venv，torch 从 PyPI 安装；全部测试约 9 分钟。

**耗时参考：** 三个种子并行训练 60k 约两天；评估每个开局约 200 s，一行 48 个开局约 2–3 小时。

# 第三部分 · 三方衔接

```
用户 ⇄ 协作窗口：方向、问题、成功标准 → 计划草案
          ⇅ 讨论（不进 git）
        上层：方法讨论；可行性与最小验证方案
          ↓ 商定后写执行单（collab/spacecraft 下 upper/run_orders/）
        下层：执行 → 交付原始数据（lower/handoffs/）
          ↓
        上层：独立重算与审查（reviews/）→ 结论回到用户与协作窗口
```

- 计划变化由用户和协作窗口发起。上层可以提出方法设想，但不单方面改计划。下层只接执行单。
- 协作窗口回答"论文要证明什么、什么算成功"；上层回答"怎样最快、最可靠地得到这个证据，以及方法上可能怎么做"。两者意见不一致时，由用户决定。
- 实验事实以 git 中的审查和交付为准。窗口内讨论得到的结论，如果要给其他窗口用，写进本文对应的一节。
- 每个窗口结束前，更新本文自己的那一节。共用部分有新事实时，通知上层修改。
