# 提交时机是状态相关的:没有常数能拿到固定设定点拿不到的东西

测于 2026-09-12,上层沙箱,h35,冻结的下层(门控已修正),**无训练、无 checkpoint**。
复算见第 5 节。这是 `docs/T10_EXECUTION_ORDER.md` §5/§6 要的 headroom 测量,
在 12 个历史种子上先做了一遍;48 种子的全量版本仍由下层执行。

---

## 1. 一句话

**固定设定点完成 8/12;按状态选择提交时机能到 11/12;而测过的每一个常数提交时机
都不如固定设定点。** 12 个种子分成两组,可行提交集**不相交**。

---

## 2. 怎么测的

上层动作是冻结的 2D `arrival_condition`,脚本驱动,不涉及任何策略:

- `commit_now` ＝ `a = (+1, ·)`,**逐位等于固定设定点 Pure MPC**(已在 262005/h35
  上逐项核对过与 `logs/terminal_gate/gate_h35.json` 相同);
- `commit_at T` ＝ t < T 发 `a = (-1, 0)`(保持**惯性冻结点**),t ≥ T 发 `a = (+1, 0)`。

栅格 T ∈ {20, 50, 80, 95, 110, 125, 140} s,目标自旋周期是 152.4 s,回合上限 300 s。
失败种子跑全部 7 个 T;完成种子跑 T = 95 和 110(反向代价)。
**全部 44 个回合 `qp_infeasible_steps` 均为 0** —— 下层清洗是干净的,这些都是任务级
结果,不是求解器产物。

分组:

- **只有 T=0 可行**:262000, 262002, 262004, 262010（4 个）
- **只有 T≥95 可行**:262001, 262005, 262011（3 个）

- 都不可行:262006（1 个）

**前两组的可行集不相交。** 这是"决策必须依赖状态"的直接形式。

### 3.2 常数 vs 逐状态

只比较在**全部 12 个种子**上都测过的提交时机:

| | 完成 | 成功平均时间 | 成功平均力冲量 |
|---|---:|---:|---:|
| 常数 T=0（固定设定点） | **8/12** | 78.6 s | **173.3 N·s** |
| 常数 T=95 | 7/12 | 184.4 s | 525.6 N·s |
| 常数 T=110 | 6/12 | 198.2 s | 538.1 N·s |
| **逐状态 oracle** | **11/12** | 108.4 s | 293.4 N·s |

T=20/50/80/125/140 只在失败种子上测过,它们分别救回 0、0、0、1、1 个,所以**上界**
就是 8/12、8/12、8/12、9/12、9/12,而且都还没减去反向代价。

### 3.3 反向代价是真实的

常数 T=110 把固定设定点本来完成的 8 个种子弄坏 4 个(262000、262002 超时;
262004、262010 破限);常数 T=95 同样弄坏 4 个。等待不是免费的:被强行等待的种子
力冲量从 130–260 N·s 涨到 414–641 N·s。

### 3.4 headroom 在已完成的种子上是免费的

oracle 在 8 个基线完成的种子上**一律选 T=0**,所以在那 8 个上它**就是**固定设定点,
逐位相同,配对燃料不变。平均燃料从 173.3 涨到 293.4 N·s 完全来自新增的 3 个完成
(406.4 / 670.5 / 764.7 N·s)。

**换句话说:多出来的 3 个完成是在原本颗粒无收的地方买到的,不是从已有的成绩上扣的。**

## 4. 这支持什么、不支持什么

**支持(闸门 B 通过):**

1. 任务级决策余量存在,而且不小 —— 8/12 → 11/12。
2. 它**不能**用一个常数拿到。测过的常数没有一个达到 8/12,更不用说超过。
3. 可行集随状态变化,且两组互不相交;262001 的窗口只有一个栅格点宽。
   这正是"需要一个状态相关的规则"的形式,也正是 `a_commit` 参数化的那个量。

**不支持 / 必须一起讲清楚:**

1. **这是 oracle,不是控制器。** T 是知道结果之后按种子挑的,它是**状态相关规则的
   性能上界**,不是可达结果。**它永远不能作为主表的一行。** 一个学习或手写的规则
   能逼近多少,是后面要测的,不是这里证明的。
2. **n=12,栅格 7 个点。** 262001 的可行集只有一个点宽,说明栅格太粗;更细的栅格
   可能救回 262006,也可能改变别的种子的集合。48 种子的全量版本仍然必须做。
3. **这不证明"必须学习"。** 它证明规则依赖状态。一个手写的状态相关规则也可能拿到
   同样的东西 —— 那正是接下来该比的对象,而不是可以跳过的一步。
4. **262006 在 7 个提交时机下全败**,与它此前"四族位置决策 + 三种姿态模式都救不回"
   的记录一致。仍按个案限制处理,不提出修复。
5. 燃料是最终判据。多出的 3 个完成每个花 406–765 N·s,是顺利完成种子的 2.4–5.9 倍。
   任何主张都必须把这条代价写在旁边。

## 5. 复算

```
# 基线（＝固定设定点）
python -B -m experiments.evaluate_arrival_condition_script --horizon 35 \
  --policy commit_now --seeds 262000 ... 262011 \
  --output logs/t10_headroom/baseline_commit_now_h35.json

# 某个提交时机
python -B -m experiments.evaluate_arrival_condition_script --horizon 35 \
  --policy commit_at --commit-time-s 95 --seeds ... \
  --output logs/t10_headroom/commit_at_T95_failing.json

# 汇总
python -B -m experiments.summarize_headroom \
  --baseline logs/t10_headroom/baseline_commit_now_h35.json \
  --sweep logs/t10_headroom/commit_at_T*.json
```

产物在 `logs/t10_headroom/`。基线那一份由 `experiments.diagnose_terminal_gate`
在同一份代码上产出,已在 262005 上逐项核对与 `commit_now` 相同。
