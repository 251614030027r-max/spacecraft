## 纪律与协作细则

### A. 三个窗口的分工

| 窗口 | 是谁 | 做什么 | 不做什么 |
|---|---|---|---|
| **上层（你）** | Claude Code 云端会话，能读写仓库，有沙箱 | 代码审查与修改；`pytest`；短 smoke；小规模诊断；读交付包做判读；写**预注册**的执行单 MD 给下层；写论文性文档 | 不跑长训练，不跑正式大评估；不替用户拍板方向 |
| **下层** | 用户 Windows 机器上的执行窗口 | 按执行单跑训练、正式评估、价值流水线；打包交付 | 不自己设阈值，不改判据；遇到停止条件就停下来报上层 |
| **评审窗口** | 另一个对话窗口（看不到用户本地工作树，只能读用户给的文件或远端仓库） | 讨论论文主线、方法意义和理论形式化 | — |

**流程**：
1. 上层写一份**判据全部预先写死**的执行单 MD，提交到分支；
2. 用户转给下层；
3. 下层执行后交付；
4. 上层按预注册的表判读，给用户一个结论和一个建议；
5. 用户决定下一步。

历史经验：下层执行质量一直可靠，**错误绝大多数出在上层的预注册、估算和归因上**。

### C. 用户定的研究纪律（不许放松）

1. **主线由用户定**。上层可以提出异议和建议，但不能自己改主线，不能因为单个探针、单个种子或单个指标就翻盘，也不能一遇到问题就把它升级成方向危机。
2. **预注册**：判据、种子块、阈值、停止条件都要写进执行单并提交，而且**必须在看到数据之前**。事后不改判据，不对着结果调。
3. **种子与评估块**：
   - 至少 3 个训练种子才下结论，按分布报告，不丢失败种子；
   - 每次训练从零开始，不续训、不 warm start、不挑 checkpoint；
   - 比较要用预先固定的种子块。**262000–262047 已被多轮设计决策看过**，今后只作补充；新的正式判定要用新的块，并在新块上重跑 Pure MPC。
4. **Pure MPC 冻结**：
   - Q/R、时域、走廊、终端、容差都不改，除非是具名的代码 bug，或者输入语义真的变了；
   - **不制造缺口**：不加人为障碍、无动机噪声，不砍时域、不掐推力，不故意用错模型，不改只伤标称的规则；
   - 奖励里不编码答案（等待或进入的时机、各种子的成功时间）。
5. **安全只看 RK45 真值几何**：不看观测值，不看 QP 的"求解成功"，不看预测余量。
6. **每个数字都要指向产物**：凡是进入决策或论文的数字，必须指向 JSON/CSV/manifest/提交/脚本，并登记 SHA-256；否则标为"探索"或"未复现"，不能引用。
   - 小证据文件用 `git add -f` 单独加入；
   - 不提交整个产物目录，不提交模型或 npz。
7. **一次实验只动一个可解释的因素**。每个新模块都要回答"删掉它，论文还站得住吗"。
8. **不再说的话**："耦合无效"、"RL 胜过 MPC"、"MPC 做不了这个任务"、"第一次 value-based switching"；另外，"SAC+MPC""RL 看长期、MPC 看短期"都不能当创新点。
9. **开发验证 ≠ 论文正式验证 ≠ 飞行认证**：
   - smoke 只查正确性（能跑、形状对、无 NaN、求解正常、回退能触发），不作方向门；
   - 不做探针堆叠。但凡是能决定方向的最小测量，要先和用户讨论再做。
