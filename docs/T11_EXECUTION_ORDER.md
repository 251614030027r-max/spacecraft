## 1. 一条提速授权(重要)

**结果型评估可以并行。** 原规则"评估必须串行单进程"的目的是保护**耗时数字**,不是
完成数和燃料。证据:上层沙箱并行 3–5 个进程跑出的 12 种子结果,与下层**串行**跑的
48 种子在共同的 12 个种子上**逐条一致**(11 个字段全同,力冲量无一超 0.01 N·s 的差)。
回合是确定性的,和进程数无关。

所以:

- **完成数 / 时间 / 燃料 / 违约 / 不可行计数 → 允许并行**,按机器核数开。
- **任何 `controller_p95`、每步耗时、实时性结论 → 仍然必须串行单进程**,单独跑。

这一条把下面 192 局从 6–12 小时压到 1–2 小时。

## 2. S7:反向代价(唯一挡住闸门 B 的事)

已经有的:48 种子基线 `commit_now` = **32/48**;16 个失败种子上六个 T 的救援数
(T=20:4, T=40:4, T=60:3, T=80:3, T=100:6, T=120:4)。

缺的:这六个 T 在**基线已完成的 32 个种子**上各弄坏多少。没有它,任何常数 T 在 48
种子上的**净完成数**都算不出来,闸门 B 无法裁。

```
# 32 个基线完成的种子 × 六个 T = 192 局，可并行
for T in 20 40 60 80 100 120 ; do
  python -B -m experiments.evaluate_arrival_condition_script --horizon 35 \
    --policy commit_at --commit-time-s $T \
    --seeds <pure_mpc_h35_48.json 里 completed=true 的 32 个种子> \
    --output logs/t11/reverse_T${T}.json &
done ; wait
```

**优先级**:机时紧就先跑 **T=100**(救援最多,6/16),它是最可能打过基线的常数。
它净完成数低于 32 就基本定调,再补其余五个确认。

## 3. 闸门 B:怎么裁

```
python -B -m experiments.summarize_headroom \
  --baseline logs/t10/pure_mpc_h35_48.json \
  --sweep logs/t10/commit_at_*.json logs/t11/reverse_T*.json \
  --output logs/t11/headroom_48.txt
```

只看它打出的 **`CONSTANT vs PER-STATE`** 那张表:

- **任何全覆盖的常数 T 追平或超过基线的 32/48** → **停,不训练**,报告。
  写死一个常数就能拿到的东西,不需要学习层。
- **全部常数都低于基线,而逐状态选择更高** → **通过**,继续 S8。

参考(上层 12 种子,另一网格):T=95 净 7/12、T=110 净 6/12,均低于基线 8/12,
逐状态 11/12。**但那是 12 个种子,不能替 48 个种子下结论。**

> 注意工具的旧提示已修正:判"常数够不够"看的是**净完成数**,不是救援侧。
> 一个救回全部可救种子、却弄坏更多的 T,是更差而不是够用。
